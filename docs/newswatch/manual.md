# newswatch 取扱説明書

設定が済んだ後の、日々の使い方と困ったときの対処です。
まだ設定していない場合は [setup.md](setup.md)、仕組みの詳細は [design.md](design.md) を参照してください。

## 何が流れるか

| 監視対象 | 投稿者名（Webhook 名の例） | 流れるもの | 流れないもの |
|---|---|---|---|
| `globallab` | グローバルラボ | グローバルラボ（韓国テスト鯖）の週次アップデート告知 | セキュリティモジュール更新、メンテナンス告知 |
| `jp-update` | 黒い砂漠 アップデート | 日本公式のアップデート告知、同日の「最新バージョンアップデート」 | セキュリティモジュール、公式ホームページ、「黒い砂漠+」の更新 |
| `jp-event` | 黒い砂漠 イベント | 日本公式のイベントタブに新しく出たイベント | — |

投稿例：

> 📢 **グローバルラボ更新**<br>
> 9월 18일(금) 업데이트 안내<br>
> https://blackdesert.pearlabyss.com/GlobalLab/ko-KR/News/Notice/Detail?_boardNo=19837<br>
> ※原文は韓国語です。ブラウザの翻訳機能で読めます。テスト鯖の情報のため、日本鯖への適用時期・内容は未定です。

- 1記事につき1メッセージです。リンクのプレビュー（カード）は出ません
- 翻訳はしません。グローバルラボの記事は、ブラウザの翻訳機能で読んでください

### 流れる時間の目安

過去の告知の傾向（2026年5〜9月）から見た目安です。公式の都合で変わります。

| いつ | 何が |
|---|---|
| 木曜 12時ごろ | 日本公式のアップデート告知（週によって水曜） |
| 同じ日の午後〜夜 | 「最新バージョンアップデートのご案内」（出ない週もある） |
| 金曜 18時ごろ | グローバルラボのアップデート告知（無い週もある） |
| 不定 | イベント告知 |

告知が出てから Discord に流れるまでは、起動の間隔の分だけ遅れます
（GAS を設定していれば 15 分程度、GitHub の定期実行だけなら数時間かかることもあります）。

**告知が無い週は何も流れません。** 正常です。

## 動いているかの確認

### GitHub の実行一覧

`https://github.com/<owner>/bdo-guild-tools/actions` → 左の **News Watch**

- 1回動くごとに1行増えます。緑のチェックなら成功です
- 行の下の表示で、何から起動されたか分かります
  - **Scheduled**：GitHub の定期実行（毎時 17 分の予定。遅れたり抜けたりします）
  - **Manually run by …**：手動、または GAS からの起動
- 右上の **Event** で `schedule` や `workflow_dispatch` に絞り込めます
- 新着が無い回は、Discord には何も流れず、コミットも増えません

### GAS の実行数（GAS を設定している場合）

GAS のプロジェクト → 左の **≡▶（実行数）**

- `dispatch`・時間主導型 の行が 15 分ごとに増えていれば動いています
- ステータスが「失敗」の行があれば、「困ったとき」を参照してください

## 止め方

| 止めたいもの | 方法 |
|---|---|
| 監視対象を1つだけ | Discord でその Webhook を削除する（GitHub 側の操作は不要） |
| 全部 | Discord で Webhook を全部削除する。または GitHub の **Actions** → **News Watch** → 右上の **…** → **Disable workflow** |
| GAS からの起動だけ | GAS で関数 `teardown` を実行する（または ⏰ **トリガー** から削除） |

Webhook を削除すると、投稿が失敗し続けるだけで、ワークフロー自体はエラーになりません。
Webhook を削除したまま Secret を残しても害はありません。

再開するときは、Webhook を作り直して Secret を差し替えます（次の項目）。

## 投稿先を変える

1. Discord で新しい投稿先チャンネルに Webhook を作る（[setup.md の手順2](setup.md#2-discord-で-webhook-を作る)）
2. `https://github.com/<owner>/bdo-guild-tools/settings/secrets/actions` を開く
3. 変えたい Secret の行の **✏️（鉛筆）** を押し、**Value** に新しい URL を貼って **Update secret**
4. 古い Webhook は Discord で削除する

Secret の Name は変えません。記録（`state.json`）もそのままで、次の新着から新しい投稿先に流れます。

## 動作を確かめたい

記録した番号を少し戻して実行すると、その間の告知が流れます。手順は [setup.md の手順5](setup.md#5-動作確認をする)。

各監視対象の直近1件だけを流したい場合は、流したい記事の番号より 1 小さい数を `last_no` に入れます。
記事の番号は、記事の URL の末尾（`_boardNo=` や `groupContentNo=` の後の数字）です。

## 記録をやり直す

`newswatch/state.json` を削除して実行すると、1回目の実行と同じ扱いになります。
その時点の最新の番号を記録するだけで、何も投稿されません。

## 監視対象を足す

公式サイトのほかの一覧（例：日本公式のお知らせタブ）も、条件を満たせば見張れます。
少し技術的な作業です。項目の意味は [design.md「ソースの設定」](design.md#ソースの設定) を参照してください。

1. 対象の一覧ページをブラウザで開き、「ページのソースを表示」で記事リンクを探す
2. リンクの URL で記事番号が入っているパラメータ名（`id_param`）と、
   タイトルの要素の `class`（`title_class`）を読み取る
3. フォーク側に `newswatch/sources.custom.json` を作り、監視対象を配列で書く
   （`newswatch/sources.json` と同じ形。1件でも `[ ]` で囲む）
4. Discord で Webhook を作り、Secret `NEWSWATCH_WEBHOOK_<ID>` を登録する
   （`<ID>` は `id` を大文字にして `-` を `_` にしたもの）
5. `.github/workflows/newswatch.yml` の `env:` に次の1行を足す
   ```
   NEWSWATCH_WEBHOOK_<ID>: ${{ secrets.NEWSWATCH_WEBHOOK_<ID> }}
   ```
   （このファイルは配布元にもあるので、配布元が同じ箇所を変えると Sync fork で衝突することがあります）
6. 手元で確認できるなら `python newswatch/newswatch.py --dry-run --source <id>` で判定結果を見る

見張れるのは、一覧が JavaScript なしの HTML で返り、記事ごとに増えていく数字の ID があるページだけです。
設定ファイルの書き方を間違えると、ワークフローが失敗（赤い ×）になります。

## 更新の取り込み

フォークのトップにある **Sync fork** → **Update branch** で、配布元の更新を取り込めます。
取り込まなくても、フォーク側はそのまま動き続けます。

配布元でも `newswatch/state.json` が更新されているため、取り込むときに `state.json` がぶつかる可能性があります（未確認）。
その場合は、**自分のフォーク側の `state.json` を残してください**。

## 困ったとき

### Discord に何も流れてこない

次の順に確認してください。

1. **告知が出ていない**だけではないか。公式サイトで新しい告知が出ているか確認する
2. GitHub の **Actions** で、実行が増えているか・緑のチェックか
3. Secret が登録されているか（Name が正しいか）
4. Discord の Webhook が削除されていないか
5. `newswatch/state.json` の `last_no` が、公式の最新の記事番号より大きくなっていないか

### 「⚠️ … の取得に … 時間失敗し続けています」と投稿された

公式サイトから一覧を2時間以上取れていません。公式サイトの作りが変わった可能性があります。
配布元が更新されていれば、**Sync fork** で取り込んでください。
取得できるようになると、自動で通常運転に戻ります（警告は一度だけです）。

一時的に重い・タイムアウトした程度では、この警告は出ません（2時間続いたときだけ出ます）。
公式サイトのメンテナンス中も出ません（メンテナンス中と判定して、黙って次の回に回します）。
ただし、メンテナンスの案内ページの作りによっては判定できず、メンテナンスが2時間を超えるとこの警告が出ることがあります
（グローバルラボは未確認）。メンテナンスが明ければ自動で戻るので、そのままで構いません。

2026-10-01 以前の版では、1回失敗しただけで「⚠️ … の取得に失敗しました」と出ていました。

### 取得できなかったときのページを確かめたい

一覧が取れなかった回（メンテナンスの案内ページに転送された・記事が0件だった・エラーが返った）は、
返ってきたページの様子が実行ログに残ります。

1. **Actions** → **News Watch** → 該当する時刻の実行 → **check** → **Check sources** を開く
2. `--- 返ってきたページ ---` の行を探す。その下に HTTP ステータス・URL・タイトル・本文の冒頭・class 名の一覧が出ています

メンテナンスの案内ページなのに警告が出てしまう場合は、ここに出ている class 名から目印を選んで、
`newswatch/sources.json` の `maintenance_markers` に足すと、次から黙るようになります。

### 「⚠️ … 公式サイトがメンテナンス中の状態が … 時間続いています」と投稿された

メンテナンス中の状態が 12 時間以上続いているという警告です。
公式で長時間のメンテナンスが告知されていれば問題ありません。そうでなければ、公式サイトの作りが変わった可能性があります。

### 「⚠️ … 日間、投稿対象の告知が見つかっていません」と投稿された

21 日間、投稿対象の告知が1件も無かったという警告です。

- 長期休暇などで告知が出ていないだけなら、問題ありません。次の告知で自動的に解除されます
- 公式サイトでは告知が出ているのに流れていない場合は、告知タイトルの書き方が変わった可能性があります。
  配布元の更新を待つか、`newswatch/sources.json` の `include` を見直してください

### 1回目の実行で何も投稿されない

正常です。1回目は最新の記事番号を記録するだけです。`newswatch/state.json` ができていれば成功しています。

### 実行が「Action required」で止まり、「GitHub detected that this workflow file may be malicious」と出る

GitHub がワークフローファイルを危険と判定して、承認待ちにしています。
配布元では、配布しているワークフローでこの表示が出ないことを確認済みです（2026-09-29。フォーク側では未確認）。
ワークフローファイルを書き換えた場合は、変更内容を見直してください。
内容に心当たりがあって問題ないと判断できる場合だけ、**Approve and run** を押してください。

### ワークフローが失敗（赤い ×）になり、「Commit state」のステップで止まっている

**Settings → Actions → General → Workflow permissions** が「Read and write permissions」になっているか確認してください。

### ワークフローが失敗（赤い ×）になり、「設定ファイルを読めません」と出ている

`newswatch/sources.json` か `newswatch/sources.custom.json` の書き方が間違っています（カンマや括弧の抜けなど）。
直前に編集した箇所を見直してください。

### 定期実行（Scheduled）が動かない・たまにしか動かない

- フォーク直後は定期実行が無効です。**Actions** タブで有効化してください
- GitHub の定期実行は、混雑時に遅れたり抜けたりします。数時間に1回しか動かないこともあります。
  告知を取りこぼすことはなく、投稿が遅れるだけです。気になる場合は GAS を設定してください（[setup.md の手順6](setup.md#6-任意gas-で起動を安定させる)）
- 60 日間リポジトリに動きがないと、定期実行が自動で停止されます。**Actions** タブから有効化し直してください

### GAS の実行が失敗する

GAS はトリガーの失敗を Google アカウントのメールに通知します。エラーの文面で原因が分かります。

| エラー | 原因と対処 |
|---|---|
| `GITHUB_TOKEN が未設定です` | スクリプトプロパティの名前か値が間違っている。⚙️ プロジェクトの設定で確認する |
| `HTTP 401` | トークンが間違っている、期限切れ、または削除された。トークンを作り直して、スクリプトプロパティを更新する |
| `HTTP 403` / `HTTP 404` | トークンに対象リポジトリや Actions の権限が無い。または `OWNER` / `REPO` が間違っている |

GAS が失敗していても、GitHub の定期実行で動き続けます（投稿が遅れるだけです）。

### Annotations に Node.js や ubuntu-latest の注意が出る

GitHub 側の実行環境の移行に関する案内です。動作に問題がなければ対応は不要です。

## できないこと

- 常設ページ（「今週のイベントは？」など）の中身の更新は検知しません。新しい記事が出たときだけ投稿します
- 複数の告知を1通にまとめることはできません
- 決まった時刻に投稿する機能はありません。新着を見つけた回に投稿します

## Webhook の URL・トークンの扱い

- Webhook の URL とアクセストークンは、コード・README・Issue・チャット・スクリーンショットに出さないでください
- 漏れた場合：Webhook は Discord で削除して作り直し、Secret を差し替える。トークンは GitHub で削除して作り直し、GAS のスクリプトプロパティを更新する
