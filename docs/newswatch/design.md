# newswatch 設計書

公式サイトのお知らせ一覧を見張り、条件に合う新着記事のタイトルと URL を Discord に投稿するツール。
見張る対象（**ソース**）は設定ファイルで増やせる。

この文書は「どう動くか」「なぜそうしたか」を書く。
導入手順は [setup.md](setup.md)、日々の使い方は [manual.md](manual.md)。

## 構成

| ファイル | 役割 | 配布元にあるか |
|---|---|---|
| `newswatch/newswatch.py` | 本体。Python 標準ライブラリのみ | ある |
| `newswatch/sources.json` | 配布しているソース（プリセット） | ある |
| `newswatch/sources.custom.json` | 利用者が足すソース | **無い**（利用者が作る） |
| `newswatch/state.json` | 状態ファイル。初回実行時に作られる | **ある**（下記） |
| `.github/workflows/newswatch.yml` | 毎時の定期実行と、状態ファイルのコミット | ある |
| `newswatch/gas/dispatch.gs` | 任意。GAS から定期的にワークフローを起動する（下記「外部からの起動（GAS）」） | ある |

`sources.custom.json` は配布元に置かない。配布元が触らないファイルなので、フォーク側で書き換えても Sync fork で衝突しない。

`state.json` は当初、同じ理由で配布元に置かない方針だった。
2026-09-30 から配布元自体をギルドの本番環境として運用しているため、配布元にもある（bot が更新する）。
**フォークして自分たちで動かす場合、Sync fork で `state.json` が衝突する可能性がある**（未確認）。
衝突したら、フォーク側の `state.json` を残す。ほかのギルドにも配るようになったら、置き場所を見直す。
また、フォークすると配布元の `state.json` もコピーされる。そのままだとフォークの1回目が初回扱いにならないため、
セットアップの手順でフォーク直後に削除してもらう（[setup.md 手順1](setup.md#1-フォークして-actions-を使えるようにする)）

## 処理の流れ

1. `sources.json` を読み、`sources.custom.json` があれば重ねる（同じ `id` は custom が上書き）
2. ソースごとに、Secret `NEWSWATCH_WEBHOOK_<ID>` が登録されているかを見る。**無いソースは飛ばす**
3. 一覧ページを取得し、記事番号とタイトルを抜き出す
4. そのソースの状態が無い（初回）なら、最新の記事番号を記録して次のソースへ。投稿はしない
5. 記録済みの番号より大きい記事を、番号の小さい順に処理する
   - 投稿対象なら Discord に投稿する
   - 対象外でも番号は進める
6. 投稿対象が `quiet_days` 日以上見つかっていなければ、一度だけ警告する
7. 状態が変わったら `state.json` を保存し、ワークフローがコミットする

ソースは互いに独立している。1つのソースの取得失敗や投稿失敗は、他のソースに影響しない。

## ソースの設定

```json
{
  "id": "jp-update",
  "name": "黒い砂漠 アップデート",
  "list_url": "https://www.jp.playblackdesert.com/ja-JP/News/Notice?boardType=2",
  "id_param": "groupContentNo",
  "title_class": "line_clamp",
  "link_attr": "data-boardno",
  "include": ["アップデートのご案内"],
  "exclude": ["セキュリティモジュール", "公式ホームページ", "黒い砂漠+"],
  "quiet_days": 21,
  "note": ""
}
```

| キー | 意味 |
|---|---|
| `id` | ソースの識別子。英小文字・数字・`-`。Secret 名と状態ファイルのキーになる |
| `name` | 投稿の見出し |
| `list_url` | 見張る一覧ページ |
| `id_param` | 記事リンクの URL で、記事番号が入っているクエリパラメータ名 |
| `title_class` | 記事リンクの中で、タイトルが入っている要素の `class` |
| `link_attr` | 省略可。指定すると、この属性を持つ `<a>` だけを記事リンクとみなす。全ページ共通の枠（スライダー等）に出る記事を除くために使う |
| `maintenance_markers` | 省略可。ページにこの文字列のどれかが含まれていたら、メンテナンス中と判定する（下記「メンテナンス中の扱い」） |
| `include` | タイトルがこのどれかを含む記事だけ投稿する。空なら全件 |
| `exclude` | タイトルがこのどれかを含む記事は投稿しない |
| `quiet_days` | 省略可。投稿対象がこの日数見つからなければ、一度だけ警告する（下記「異常時の動き」）。0 または省略で見張らない |
| `note` | 投稿の末尾に付ける一文。空なら付けない |

**Secret 名**は `NEWSWATCH_WEBHOOK_` ＋ `id` を大文字にして `-` を `_` にしたもの。
例：`jp-update` → `NEWSWATCH_WEBHOOK_JP_UPDATE`

### 読み取りの規則

- `<a href="...">` のうち、`href` のクエリに `id_param` が数字で入っているものを記事リンクとみなす
  （`link_attr` があれば、さらにその属性を持つものだけ）
- タイトルは、そのリンクの中で最初に出てくる `class` に `title_class` を含む要素のテキスト
  - リンク内の全テキストを使わないのは、カテゴリ名・日付・副題が混ざるため
  - 最初の1つだけにしているのは、副題にも同じクラスが付くページがあるため（日本公式のスライダー）
- 同じ記事番号が一覧に何度出ても、最初に出たものを使う
- HTML の数値参照（`&#xC5C5;` など）は文字に戻してから判定する

### 見張れるページの条件

一覧が JavaScript なしの HTML で返ること、記事ごとに**増えていく数字の ID** があること。
この2つを満たさないページは、このツールでは見張れない。

ソースの足し方（手順）は [manual.md「監視対象を足す」](manual.md#監視対象を足す)。

## 配布しているソース

### globallab — グローバルラボ（韓国テストサーバー）の週次アップデート告知

- 一覧：`https://blackdesert.pearlabyss.com/GlobalLab/ko-KR/News/Notice?_categoryNo=2`（Updates タブ、韓国語版）
- 投稿対象：「업데이트 안내」を含み、「보안 모듈」（セキュリティモジュール）を含まないもの
- 投稿の末尾：原文は韓国語であること・日本鯖への適用は未定であることの注記
- **翻訳はしない。** 原文 URL を渡し、中身はブラウザの翻訳機能で読んでもらう
- URL は取得元に合わせて ko-KR 版。en-US 版と ko-KR 版で記事番号は同じ（2026-09-29 に確認）

2026-09-29 に実物で確認したこと：

- 英語版（en-US）のページでもタイトルは韓国語のまま。タイトルは HTML 数値参照で書かれている
- 記事は上部スライダー（`a.news_item`）と本体一覧（`a.board_item_inner`）の2か所に出る。タイトルは `<p class="title line_clamp">`
- 本体一覧は 24 件。そのうち投稿対象が 18 件、除外が 6 件（すべて「보안 모듈 최신 버전 업데이트 안내」）
- 記事番号（`_boardNo`）は新しいほど大きいが、連続はしない（理由は未確認）。2026年7月上旬に 13393 → 19540 と飛んでいる
- 記事を編集してもタイトルに「(최종 수정 : …)」が付くだけで、番号は変わらない

投稿時刻の傾向（2026-09-30 に記事ページの日時から集計）：

- 5/22〜9/18 の 18 件中 15 件が**金曜 18:00（日本時間）**。例外は 8/28（金）19:00、7/26（日）14:00、7/16（木）18:00
- 記事ページの表記は「12:00 (UTC+3)」。なぜ UTC+3 表記なのかは不明。
  タイトルの修正時刻（「최종 수정 : 2026-09-04 18:05」など）が投稿直後になっており、日本時間 18:00 と読むと整合する
- アップデートが無い週は「정기점검 미진행 안내」（定期メンテナンスを実施しない告知）が出る（例：9/25）

### 日本公式（jp-update / jp-event）の共通事項

2026-09-29 に実物で確認したこと：

- ニュース一覧は `https://www.jp.playblackdesert.com/ja-JP/News/Notice`。
  タブ（カテゴリ）は `boardType` で切り替わる：1 お知らせ／2 アップデート／3 イベント／4 GMノート／5 パール商店
- 記事リンクは `/News/Notice/Detail?groupContentNo=<番号>&countryType=ja-JP`
- **上部スライダー（`div.news_item`）は全タブ共通。** どのタブを開いても、カテゴリに関係なく同じ数件が出る。
  スライダーのリンクには `data-boardno` 属性が無く、本体一覧のリンクにはある
  → `link_attr: "data-boardno"` でスライダーを除く
- スライダーでは、タイトルと副題の両方に `line_clamp` が付いている
- **一覧は最終更新順に並ぶ。** 「今週のイベントは？」（6013）、「お知らせ情報まとめページ」（8096）、
  「現在使えるクーポンまとめ！」（7077）のような常設ページは、中身が更新されると一覧の上の方に戻ってくる。
  番号は古いままなので、このツールでは**新着として扱わない**（下記「できないこと」）
- **ホームページのメンテナンス中は、一覧ページが案内ページに転送される**（2026-10-01 08:00〜10:00 のメンテナンスで実物を確認）。
  一覧を頼むと `302 Found` で `/ja-JP/shutdown/closetime?shutDownType=0` に転送され、転送先は HTTP 200 で
  「ただいまサーバーメンテナンス中です」と対象・日時を書いたページを返す。本文に `class="closetime_wrap"` がある。
  普段の一覧ページは転送されない（2026-09-29 に確認）

## 投稿内容

```
📢 **<name>**
<記事タイトル>
<記事URL>
<note（あれば）>
```

- **リンクの埋め込みプレビューは出さない**（Discord の `flags: 4` = SUPPRESS_EMBEDS）。
  公式の OGP は汎用の画像とタイトルで、情報にならないため
- 1記事＝1メッセージ。同じ回に新着が複数あれば、番号の小さい順に続けて投稿する

## 状態ファイル

`newswatch/state.json`

```json
{
  "globallab": { "last_no": 19861, "last_target_date": "2026-09-30" },
  "jp-update": { "last_no": 12653, "last_target_date": "2026-09-30" }
}
```

| キー | 意味 |
|---|---|
| `last_no` | 処理済みの最大の記事番号。これより大きい記事を新着とみなす |
| `last_target_date` | 最後に投稿対象を投稿した日（UTC）。初回実行日で初期化される |
| `fail_since` | 取得に失敗し始めた時刻（UTC）。取得に成功すると消える |
| `error_notified` | 取得失敗の警告を投稿済みなら `true`。取得に成功すると消える |
| `quiet_notified` | 無投稿の警告を投稿済みなら `true`。投稿対象を投稿すると消える |
| `maint_since` | メンテナンス中と判定し始めた時刻（UTC）。取得に成功すると消える |
| `maint_notified` | メンテナンス長期化の警告を投稿済みなら `true`。取得に成功すると消える |

- 各ソースの初回は投稿せず、その時点の最新番号を記録するだけ（過去分の一斉投稿を防ぐ）
- `last_no` を小さく書き換えて実行すれば、その間の告知が再投稿される（動作確認用）
- あるソースの記録を消せば、次回そのソースは初回扱いに戻る
- `last_target_date` が無い古い状態ファイルは、次の実行日を起点に補われる

## 異常時の動き

| 状況 | 動き | ワークフロー |
|---|---|---|
| Secret 未登録のソース | 何もしない | 成功 |
| 一覧の取得・解析に失敗（タイムアウト、記事0件も含む） | 何も投稿しない。`fail_since` を記録する | 成功 |
| 取得失敗が 2 時間以上続く | そのソースの投稿先に警告を**一度だけ**出し、`error_notified` を立てる。以降は黙る | 成功 |
| 取得失敗の後に復旧 | `fail_since` と `error_notified` を消し、通常運転に戻る | 成功 |
| 投稿に失敗（Webhook 削除・一時障害） | その記事の手前で止め、番号を進めない。次回に再試行 | 成功 |
| 警告の投稿にも失敗 | `error_notified` を立てない（次回また警告を試みる） | 成功 |
| メンテナンス中と判定（下記） | 何も投稿しない。`maint_since` を記録する | 成功 |
| メンテナンス中の判定が 12 時間以上続く | 投稿先に警告を**一度だけ**出し、`maint_notified` を立てる | 成功 |
| 投稿対象が `quiet_days` 日以上見つからない | 投稿先に警告を**一度だけ**出し、`quiet_notified` を立てる。次に投稿対象を投稿すると解除 | 成功 |
| 設定ファイルが読めない | 何もしない | **失敗** |

**無投稿の警告を入れた理由**：告知タイトルの書き方が変わって `include` の語を含まなくなると、
一覧の取得は成功し続けるので、取得失敗の警告では気づけない。黙って投稿が止まるこの壊れ方を、日数で拾う。
告知が本当に出ていないだけ（長期休暇など）でも出るので、警告文もそう書いてある。
配布ソースの `quiet_days` は 21 日。週次の告知が2回続けて無い程度では鳴らないように、という仮の値

**取得失敗を 2 時間待ってから警告する理由**：2026-10-01 21:16 に、日本公式アップデートの一覧が一度だけタイムアウトし
（`The read operation timed out`）、即座に警告が出た。直後には 0.4 秒で取れており、一時的な重さだった。
一瞬の重さで警告が出ないよう、失敗が続いたときだけ知らせる。GAS の 15 分間隔なら 2 時間で 8 回ほど試す。
2 時間は仮の値。メンテナンス（12 時間）と分けているのは、メンテナンスでもないのに取れない状態が続くのは
本当に壊れている可能性が高いため。それ以前は1回の失敗で即座に警告していた。

**ワークフローを基本的に失敗扱いにしない理由**：失敗扱いにすると、リポジトリのオーナーに毎時失敗メールが届く。
異常は投稿先チャンネルで気づける設計にしてある。

**設定ファイルの読み込み失敗だけ失敗扱いにする理由**：起きるのは利用者が設定を書き換えた直後で、
投稿先も分からない状態なので、Actions の失敗表示で気づいてもらう。

**Webhook を削除すれば止まる理由**：投稿が失敗し続けるだけで、ワークフローは成功で終わる。
リポジトリ側の操作は不要。

### メンテナンス中の扱い

次のどちらかに当たったら、取得失敗ではなく**メンテナンス中**と判定し、警告せずに次の回に回す。

1. 一覧ページを頼んだのに、別のパスのページに転送された（全ソース共通）
2. ページに `maintenance_markers` の文字列が含まれている（日本公式は `closetime_wrap`）

**入れた理由**：2026-10-01 08:00 の日本公式ホームページのメンテナンスで、案内ページには記事が1件も無いため
「取得に失敗しました」の警告が出た。メンテナンスは定期的にあり、そのたびに警告が出るのは困る（作者判断）。

**12 時間で知らせる理由**：メンテナンスページの作りが変わる、判定を誤る、などで黙り続けないための保険。
12 時間は仮の値（2026-10-01 のメンテナンスは 2 時間予定だった）。

**グローバルラボ**：メンテナンス時の挙動は未確認。転送で案内ページに飛ばす作りなら 1 で判定される。
そうでなければ取得失敗として扱われ、2 時間続くと警告が出る。

**目印を後から足すための記録**：一覧が取れなかったとき（転送された・記事0件・HTTP エラー）は、
返ってきたページの HTTP ステータス・URL・title・本文の冒頭・class 名の一覧を実行ログに書き出す
（`--- 返ってきたページ ---` の行）。グローバルラボのメンテナンスに当たったら、ここから目印を選んで
`maintenance_markers` に足す。タイムアウトのようにページ自体が返ってこない場合は記録されない（2026-10-01 追加）

## 実行

- 毎時 17 分（UTC。日本時間でも毎時 17 分）。告知が無い時間帯に何も投稿されないのは正常
- Secrets はソースごとにワークフローの `env` で1つずつ渡す。
  当初は `toJSON(secrets)` でまとめて渡していたが、GitHub に「悪意のある可能性があるワークフロー」と判定され、
  承認するまで実行されなかった（2026-09-29）。Secrets を丸ごと渡す書き方は、Secrets を抜き出す手口と同じ形のため。
  判定の理由は GitHub から明示されておらず、これが原因というのは推測。明示に変えた後は警告なく実行された（2026-09-29）
- `concurrency: newswatch` で、実行が重ならないようにしている
- `state.json` のコミットの前に `git pull --rebase` する（他のツールが同時にコミットした場合への備え）
- 公開リポジトリは 60 日間動きがないと定期実行が止まる。新着のたびに `state.json` がコミットされるので、その延命も兼ねる
- **GitHub の定期実行は抜けやすい。** 2026-09-30 の観測では、04:17〜17:17（日本時間）の予定 14 回のうち
  実際に動いたのは 3 回（04:26 / 08:45 / 14:39）。遅れも 9〜28 分あった。
  抜けても告知を取りこぼすことはない（一覧に過去の告知が並んでいるので、次に動いた回で拾える）が、投稿が数時間遅れうる。
  安定させたい場合は、下記「外部からの起動（GAS）」で補う

## 外部からの起動（GAS）

GitHub の定期実行の抜けを、Google Apps Script（GAS）の時間主導トリガーで補う。**任意。**
GAS から GitHub の API でワークフローを手動実行（`workflow_dispatch`）させる。スクリプトは `newswatch/gas/dispatch.gs`。
設定手順は [setup.md「GAS で起動を安定させる」](setup.md#6-任意gas-で起動を安定させる)。

- GitHub の定期実行はそのまま残す。GAS が止まっても、定期実行だけで動く状態に戻るだけで、監視は止まらない
- GAS から起動した回は、Actions の一覧で「Manually run by <トークンの持ち主>」と表示される
- 起動の間隔は 15 分（`EVERY_MINUTES`）。GAS のトリガーは指定時刻ちょうどではなく幅を持って起動するが、
  この用途では数分のずれは問題にならない
- **起動できるのは、トークンで許可したリポジトリだけ。** フォークを安定させたい場合は、フォークの持ち主が自分で設定する
- **リトライは入れていない。** 15 分ごとに起動するので、次の起動がそのままリトライになる。
  スクリプト内で再試行を重ねると、GitHub 側の一時障害時に同じ実行を二重に起こすおそれがある
- トークンは Fine-grained token を**無期限**で使う。GitHub のドキュメントでは、個人アカウントなら無期限にできる
  （組織が上限を決めている場合を除く）。期限切れで止まるのを避けるため。
  代わりに権限を「対象リポジトリの Actions: Read and write」だけに絞り、漏れたときにできることを限る

### GAS と Cloudflare Workers の比較（2026-09-30 に GAS を選んだ理由）

| | GAS | Cloudflare Workers |
|---|---|---|
| 作る手間 | スクリプトを貼ってトリガーを設定するだけ | Worker を作り、cron とシークレットを設定する |
| 起動時刻の正確さ | 幅がある。この用途では問題にならない | 正確だと言われている（未確認） |
| 異常に気づけるか | トリガー失敗が Google アカウントにメール通知される | 自分で見に行かないと気づきにくい（確度中） |

差は小さく、慣れ・手軽さ・失敗通知の3点で GAS を選んだ。外部の cron サービス（cron-job.org 等）は、
GitHub のトークンを第三者に預けることになるため採らなかった。

## できないこと

- **番号が変わらない記事の更新は検知できない。** 常設ページの書き換えや、既存記事への追記は投稿されない
- JavaScript で一覧を描画するページ、記事ごとの数字 ID が無いページは見張れない
- 決まった曜日・時刻に投稿する機能は無い。新着を見つけた回に投稿する
- 複数の新着を1通にまとめる機能は無い
